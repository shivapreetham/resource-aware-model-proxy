Local LLMs · Memory

I gave my model more context and my GPU got emptier

I set out to build an assistant, killed my laptop instead, and ended up writing a daemon that resizes the model rather than freezing the machine.

Measured on 16 GB RAM · RTX 5060 Laptop 8 GB · Qwen2.5 and Llama 3.1

I was not trying to build a memory manager. I was building an assistant on top of a local model, and one afternoon the machine simply stopped. Out of memory. The cursor stopped moving, Ollama died, and I lost the session I had been working in. Nothing crashed gracefully; the whole desktop just went under and stayed there for a minute.

If you run models locally, you have had some version of this afternoon. The fix everyone reaches for is to pick a smaller model and stop thinking about it — which works, and costs you a worse assistant every hour of every day to prevent something that happens occasionally. The alternative is to keep the big model and accept that your machine is periodically unusable.

Both options seemed wrong for the same reason: they are one-time decisions about a constraint that changes minute to minute. So before writing anything, I went looking for where the cliff actually sits. The first measurement contradicted my mental model entirely.

The measurement that made no sense

I loaded Llama 3.1 8B on an 8 GB card three times, changing only the context length, and watched free VRAM after each load.

default2,516 MiB

Look at the last row. I asked for more context — more KV cache, more memory — and got 684 MiB of VRAM back. That is not how memory works.

The explanation is in the other number I wasn't watching. System RAM had dropped to 1,509 MB. The KV cache at 40k tokens no longer fit on the card, so the runtime quietly moved layers onto the CPU. Doing that freed VRAM and consumed RAM instead.

VRAM pressure had silently become RAM pressure. Nothing announced it.

The arithmetic behind it

This is entirely predictable once you count the KV cache, which most capacity planning ignores. Every generated token stores a key and a value vector in every layer, and that store grows linearly with context length:

kv_bytes_per_token = 2 · n_layers · n_kv_heads · head_dim · bytes_per_element 2 both a key and a value are cached n_layers transformer blocks, each caching independently n_kv_heads attention heads sharing a KV projection (GQA) head_dim width of one head bytes_per_element 2 for fp16

For Llama 3.1 8B — 32 layers, 8 KV heads, head dimension 128, fp16 — that is 128 KiB per token. So the full 40,960-token window costs:

2 · 32 · 8 · 128 · 2 = 131,072 bytes ≈ 128 KiB / token 128 KiB · 40,960 tokens = 5.0 GiB KV cache alone 5.0 GiB + 4.9 GiB = 9.9 GiB + Q4 weights > 8.0 GiB card capacity

The cache alone exceeds the weights. Nothing was mysterious about that measurement: the request simply did not fit, and the runtime resolved the overflow the only way it could — by moving layers into system RAM. The surprise was only that it happened silently, and that the resource which looked healthier afterwards was the one under pressure.

This is the thing that makes local LLMs so annoying to live with. The shortage doesn't stay put. Any tool watching only one resource will draw the wrong conclusion, and any human tuning by feel is chasing a number that moves when they touch it.

Choosing continuously instead of once

If the constraint changes minute to minute, the model size should too. I built RAMP — a small daemon that sits in front of Ollama or llama.cpp, watches RAM, VRAM and disk every few seconds, and moves the loaded model up and down a ladder.

Open Chrome with forty tabs and your 7B quietly becomes a 3B. Close them and the 7B comes back. Your tools never know: it speaks the OpenAI API, so the integration is one line. 

- client = OpenAI(base_url="http://localhost:11434/v1")   # to Ollama
+ client = OpenAI(base_url="http://localhost:8090/v1")    # through RAMP

The asymmetry is the whole design. Dropping late means your machine freezes; climbing back late costs a slightly worse answer for another minute. So it drops in about six seconds and takes over a minute to come back.

The decision rule

A tier is admissible when its footprint plus a reserve fits every budget it touches. Both resources must clear independently — a tier that fits RAM but not VRAM is not a candidate:

fits(t) ⟺ ram(t) + M ≤ R and vram(t) + Mv ≤ V M, Mv reserve kept free for the rest of the machine R, V free RAM and free VRAM

The subtlety is which R to use. Comparing against currently-free memory makes upgrades impossible, because the memory an upgrade needs is occupied by the model it replaces. The budget is therefore counted post-swap:

R′ = R + ram(current) what is free once the current tier unloads

And because the controller's own actions move the signal it reads, a single threshold oscillates: unloading frees memory, which justifies reloading, which consumes it again. Two separated thresholds and a time requirement break that loop:

down ⟸ R < M for k consecutive samples up ⟸ ram(t) + M + E ≤ R′ema sustained for T seconds E extra headroom, so a promoted tier does not immediately consume the margin that justified promoting it k 2 samples (~6s) T 90s E ~1 GB R'ema smoothed, so a momentary dip cannot cancel a recovery

Downgrades read the raw signal and upgrades read a smoothed one. That is deliberate: reacting late to pressure is expensive, reacting late to recovery is not.

Two seconds is the number that makes the approach viable at all; swapping was assumed to be too expensive to do casually. It is not, because the operating system keeps recently-read weights in its page cache. A useful consequence follows: when pressure is severe enough to evict that cache, it is the upgrade that becomes slow, never the downgrade. Cost asymmetry aligns with urgency asymmetry.

And since "the memory watchdog is the leak" is the obvious retort, RAMP reports its own footprint. You can check rather than trust me.

What testing did not catch

The suite stands at 166 tests. None of the three defects below was caught by it — each surfaced only under a running system, and each is a category worth naming.

A controller that misread its own transient state

A pinned tier reverted itself two seconds after being set. Mid-swap, the old backend is stopped before the current-tier variable is updated, so for a window the daemon appears crashed to itself. Crash recovery fired and restored the tier the swap was replacing. The fix is to treat a transition in progress as a state no decision may be made about; the general lesson is that any system observing itself must distinguish "broken" from "mid-change."

Worth recording: the first regression test for it passed against the broken code, because it did not wait long enough for the spurious recovery to land. A regression test not yet watched to fail is not evidence of anything.

Cleanup that only ran on the happy path

RAMP can occupy the port a model server already uses and relocate that server one port over, so every client routes through it unmodified. Restoration ran on clean exit — and only on clean exit. Killing the daemon rather than stopping it skipped the handler entirely and left nothing on port 11434. The arrangement is now journalled to disk when engaged, so it survives a hard kill and can be repaired on the next run.

An estimate conservative enough to be wrong

The most instructive of the three, because it produced no error at all. A GPU-resident model was charged its weights against system RAM and VRAM — double-counting a quantity that exists once. A 5 GB model was billed 6.7 GB of RAM it never touched, so the top of the ladder required 8.8 GB free on a 16 GB machine and was unreachable in practice. The daemon declined to use the best model installed and reported itself healthy throughout. Over-conservative estimates are not the safe direction; they are simply a different way to be wrong.

A green suite on one machine proved to be the weakest signal available. Continuous integration caught a defect already declared absent.

Scope and coverage

RAMP is verified end to end against Ollama: detection, relocation, the full pressure cycle, crash recovery, and restoration. The llama.cpp and LM Studio paths run through the same policy and lifecycle code and are covered by unit tests including every refusal branch, but have not had an integration run against those binaries. The design anticipates that gap rather than papering over it — where RAMP cannot positively identify a runtime, or cannot reconstruct the command needed to restart it, it declines and changes nothing. Stopping a server you cannot restart is the one outcome worth engineering against absolutely.

The open measurement is swap frequency over a multi-hour workload. Per-swap cost is characterised (1.9 s warm, 16.5 s cold); the rate at which swaps occur is a function of the machine and the work being done on it, so quoting a figure from one laptop would be worth less than instrumenting it. ramp status reports swaps per hour, cumulative time spent swapping, and per-tier occupancy directly — the claim is checkable rather than asserted.

Reports from other hardware are the most useful contribution right now, particularly from anyone running llama.cpp or LM Studio.

Running it

pip install ramp-llm
ramp demo      # no models downloaded - watch it switch
ramp watch     # in a second terminal
ramp stress    # in a third: fill memory, watch it drop

The demo runs against stand-in servers that announce which size answered, so the behaviour is visible in plain text with nothing to download. With Ollama installed, plain ramp finds your models and builds the ladder itself. If you have ever lost an afternoon to an OOM on your own machine, this was written for you.
